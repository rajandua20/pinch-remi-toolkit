Sunday 26 July

DAY 3 · IN PROGRESS
  • SUN · 01Two prod fixes. The Finance Console tabs all errored — root cause was a real async-context bug: credentials were bound inside an awaited helper, so AsyncLocalStorage.enterWith didn't survive the return and every query ran unauthenticated. Bound in-handler instead. Separately, the sandbox 503'd because Amplify passes console env to the build but not the SSR runtime — PINCH_MCP_URL is now baked into next.config alongside the other server vars.
  • SUN · 02Agent widgets wired end-to-end. The LyboAI widget injectors existed but were mounted nowhere; now the back-office Remi bubble and the public Front Desk both render. Added a per-coach backend Remi key, a guided Next/Back onboarding wizard plus a Settings tab to enter both agent keys, a "Test connection" check, and a connect→console auto-refresh so setup no longer dead-ends.
  • SUN · 03Managed-agent lock-down. On LyboAI, a managed org's Remi core is now locked server-side — a business can skin the agent (name, avatar, welcome, theme) and add knowledge, but can't rewrite the prompt, guardrails, tools or channels, or remove the seeded RAG. Keeps integrity while each business still makes it their own. QR tool folded into the seeded preset (23 tools); the deploy script was split so a deploy ships code only and can never clobber env/secrets.
  • SUN · 04Business vs. coach — resolved. The Pinch merchant id is business-level (keys live per tenant), so Payments & Billing and Integrations moved into the business portal, with a Business↔Coach switcher for accounts that are both. The gate is tenant ownership, not a role — because a solo coach owns their own individual tenant without the tenant_owner role. A staff coach (member, not owner) gets a reduced portal: their profile, courses and a "My earnings" view, but no merchant finance, agents, site or plan controls.
  • SUN · 05Per-coach revenue attribution. One business = one Pinch merchant account (not a Pinch app per instructor). Transactions are tagged with a coachId in Pinch metadata — the attribution pattern Pinch's own team endorses, since there's no first-class coupon/tag concept — and the finance console adds a Coach column and a Group-by-coach split. A staff coach sees only their own.
  • SUN · 06Seeders + real payments. A staff coach and learners per business, and a per-coach payments seeder that produces real sandbox transactions on Pinch's hosted page — a successful direct debit, a dishonoured direct debit, and a card link paid with a test card — each attributed to a coach. Payments demo runbook written.

Challenges & opportunities

The calls that shaped the build

The decisions that set the direction — and, below, the challenges we turned into product opportunities. Kept high-level; the deep technical notes live in the repos.

Decisions that set the direction

DECISION A

Build an MCP server at all

One Pinch core, portable across Claude, Cursor and LyboAI — every host gets the same tools instead of three bespoke integrations.

DECISION B

Approve-then-act, enforced in code

Every write refuses without confirm:true and returns a preview — the gate lives in the tool layer, not the prompt, so no host can move money without a human step.

DECISION C

"MCP is not the moat"

Repositioned as an augmented product line — Design · Do · Ask · Fix across three surfaces — with the MCP server as one pillar, not the pitch.

DECISION D

BYO keys, no aggregation

Each business owns its merchant relationship with Pinch directly — cleaner compliance, and every platform adoption grows Pinch's merchant base.

DECISION E

Two agents, not one

Back-office Remi and customer-facing Remi Front Desk carry different privileges — the customer-facing agent gets a restricted tool subset by construction.

DECISION F

A toolkit for others — not an open server

The MCP server stays proprietary. What we share is the toolkit — integration recipes, the security guide and patterns — so others can build safely on Pinch. The value is the product line, not the server binary.

DECISION G

Gate the hosted MCP server

Move the hosted endpoint from an open relay to a gated service: a login / registration step, per-merchant domain registration, and headless operation. Today IAM + a shared-secret header gate it; the login + domain-registration console is a Polish-Week build.

DECISION H

The business is the merchant

The Pinch merchant account is per business, not per coach — so Payments & Billing and Integrations live in the business portal, gated by tenant ownership (a solo coach owns their own tenant; a staff coach doesn't). A Business↔Coach switcher serves accounts that are both. Individual coaches within a business are attributed with a coachId in Pinch metadata, so one account's transactions split per coach — no separate Pinch app per instructor.

Earlier Friday calls that still stand: the Do / Ask / Fix triad from the ~19:50 huddle (later extended with Design); payment-link-first collections for the hackathon, with metadata passthrough for correlation instead of fragile description markers; split payments brought in-scope as an underserved shared-cost wedge for service businesses (~22:30 founder call), with exposure thresholds of >14 days or >25% of total; and statement of accounts added now, with Xero and the report suite deferred to the roadmap — First Submission locks the concept Sunday, and Polish Week forbids new features.
