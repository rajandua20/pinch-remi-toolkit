Demo runbook

Remi × Pinch — what to demo, how, and what to expect

A live 5–10 minute walkthrough against the Pinch test environment. Where a step has a caveat, it's called out so nothing surprises you on stage. Remi is named for remittance — the safe movement of money is the one job it exists to do.

0 — Pre-flight

Do this before you present.

  • pinch-mcp is live: curl https://<url>/healthz → {"ok":true}, and /meta → "toolCount":23. If not, redeploy (SETUP §3).
  • PINCH_MCP_URL set in CoachPlus (Amplify + .env.local).
  • Smoke test green: node demo/test-mcp.mjs with a set of Pinch test keys.
  • Signed in as a demo coach (own Pinch keys), on /coach/payments-lab.
  • Test card handy: 4242 4242 4242 4242, any future expiry/CVC.
  • Fallback artifacts: split spl_Bh8QfH0Rai, dishonour pmt_lOb1nrunAStqfs, marked link plk_FQbR4SXNx7hdZr.
One honest caveat: the Pinch sandbox does not fast-forward an overnight direct debit via the API (Time-Travel is accepted but doesn't flip scheduled DD). Demonstrate a dishonour through the synchronous payment-link path (a #code marker + the test card), not by advancing the clock.

1 — The MCP server & its guardrails ≈1 min · the foundation

"The base is the first MCP server for Pinch — 23 tools, every write confirm-guarded in the tool layer, not the prompt."

Do

On the landing playground (or Claude Desktop), call a write tool without confirm — e.g. pinch_create_refund.

Expect

A structured preview (preview:true, wouldDo) and no API call. Re-call with confirm:true to execute. Note the refund cap and that the public endpoint refuses live.
[ screenshot: playground preview vs confirmed ]

2 — Remi designs the billing ≈1.5 min · Design

"A coach describes pricing in plain English; Remi turns it into a deterministic blueprint and sets it up — no dev work."

Do

In Remi (LyboAI) or the playground: "Set up my swim school: $59/week for 10 weeks with a $100 deposit, direct debit."

Expect

A blueprint preview (deposit + 10 instalments, first/last dates, term total, indicative fees), then a Pinch plan + subscription. No stored method → pendingSetup:true + a setupLink (the correct two-step). This is the direct-debit term demo.
[ screenshot: Remi blueprint + approval ]

3 — CoachPlus, in-platform ≈3 min · the platform story

The platform now does these itself via the MCP engine. Use the Payments Lab (/coach/payments-lab) so it's fast and reliable on stage.

3a. Simulator — mock mode (instant, no keys). Run the simulator with mode mock.

Expect

A scripted scenario + Remi's findings: 3 dishonoured payments (insufficient-funds / expired-card / blocked-by-bank) each diagnosed, a silently-stalled subscription (39 days), and a split with the largest outstanding exposure named. The "Remi catches what you'd miss" moment.
[ screenshot: Payments Lab → mock simulation result ]

3b. Simulator — sandbox mode (real artifacts). Run with mode sandbox, scenario all.

Expect

Real ids/links: a #insufficient-funds payment link, a term subscription, a 3-way split, a discounted collect (WELCOME20). Pay the marked link with 4242… → it dishonours immediately and appears in the needs-attention feed.

3c. Discount code on a customer payment. Collect $59 with code WELCOME20, Execute.

Expect

The hosted link is created for $47.20 (20% off), the code + saving recorded. A 100%-off code activates with no Pinch charge.

3d. Refund / cancel. Preview first (capped), then Execute.

[ screenshot: Payments Lab → discount + QR result ]

4 — QR to get paid ≈45 sec · anyone can pay

Do

In Payments Lab, run QR for a $59 session with a vendorEmail, Execute.

Expect

A hosted link plus a scannable PNG QR and a vendor-notification tag. Scan it with a phone → Pinch's hosted checkout. The "payment received" notification is delivered by the CoachPlus webhook on completion (the MCP server never sends outbound mail).
[ screenshot: QR rendered in Payments Lab + phone scan ]

5 — Dishonour → diagnosis → recovery ≈1 min · Fix

Do

Open the needs-attention feed after 3b, pick the failed payment, approve the retry.

Expect

A plain-English diagnosis (ownership: customer / merchant / platform), a drafted customer message, and — on approval — a soft failure retried +3 days (the #code stripped from the clone so it succeeds), or a hard failure routed to a fresh card link.
[ screenshot: needs-attention feed + recovery ]

6 — Security, if asked ≈45 sec · the differentiator

"The security model is the product. No card or bank field exists anywhere in the 23 tool schemas — payment details are captured on Pinch's hosted page, never in the app, the model, the transcript or an MCP request."

Expect

Confirm-guard preview / live refusal / capped refund — the guardrails hold at the tool layer. Show the data-handling boundaries on the hackathon page.

What's real vs. what's polish

Real, verified against the sandboxPolish / caveat
Subscriptions (weekly/fortnightly/monthly, terms, deposits), direct-debit collection, dishonour diagnosis + retry, refunds, splits, discounts, QR links, webhook GST invoices.The CoachPlus payment actions call the MCP engine today; a native direct-REST path is a Polish-Week item.
Remi issue detection: dishonour taxonomy, stall detection, split exposure, needs-attention feed.Discounts are a reduced amount, not a first-class Pinch discount object; 100%-off skips Pinch. Time-Travel won't fast-forward overnight DD — demo dishonours via the synchronous link path.

If something breaks on stage

  • MCP errors / "PINCH_MCP_URL is not set" → §0 pre-flight; fall back to the mock simulator (no keys) and the pre-seeded artifacts.
  • Hosted pay page won't load on a locked network → open it on a phone/hotspot.
  • Anything flaky → the landing playground demo mode replays captured real sandbox outputs offline.
